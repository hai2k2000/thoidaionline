# Database Management V1 Foundation Design

## Scope

This design implements the owner-approved local-only foundation for the Database Management V1 module. It does not authorize production migration, VPS storage creation, Google Drive API access, merge to `integration/production`, or deployment.

## Boundaries

- Existing Next.js App Router, HMAC session, server-only Supabase client and RBAC remain the only application/authentication path.
- New tables use the `db_` prefix in the existing PostgreSQL database.
- Browser clients never access the new tables directly; server routes use session/RBAC checks and the service-role query path.
- File bytes are stored by a provider-neutral adapter. Local default storage is outside the checkout; production storage must be supplied explicitly outside the release root.
- Google Drive is metadata-only in this phase: URL, provider, media kind, usage rights and link status.

## Data model

`db_categories` and `db_record_types` define the multi-level catalog. `db_form_definitions` and `db_form_fields` provide versioned, controlled forms; fields have an explicit type, required/searchable flags, options and validation JSON. `db_records` stores the common identity and bounded metadata. Files, external links, keywords, relations, ACL rows, history and saved filters are separate tables with foreign keys and indexes.

The record search document is generated by a database trigger from code/title/summary/metadata. It is an initial bounded search path; field-specific indexes and richer AND/OR/NOT query planning are Phase 3 work.

## Authorization contract

The permission catalog adds `record.discover`, `record.metadata.view`, `record.preview`, `record.download`, `record.create`, `record.edit`, `record.approve`, `record.delete`, `record.restore`, `record.export` and `record.acl.manage`. Explicit user denies continue to take precedence in the shared RBAC resolver.

Record ACL rows are evaluated only after catalog permission resolution. A deny for the matching user/role/department overrides any allow. Search filters unauthorized rows before returning the result set; download/preview must repeat the decision immediately before reading bytes or creating a signed URL.

## API contract

`GET /api/database/records?q=` returns only non-deleted records visible to the authenticated actor. `POST /api/database/records` requires same-origin mutation, validates all IDs/metadata/links, requires `record.create`, writes through the server-only repository, and emits an audit event. Update/detail/search/file routes will be added in the subsequent phases using the same contract.

## Local runtime and storage

The local database must run in the repository's isolated Supabase/PostgreSQL stack. The current machine has Supabase CLI installed, but Docker is not currently running; migration execution is therefore a pending local-environment step. No production database or VPS checkout is used.

The storage adapter accepts only approved office-document MIME types, enforces a 50 MiB limit, generates a UUID-based key under the record ID, writes with exclusive creation, and records SHA-256. It does not expose a static path. A production root must be approved and backed up independently from releases.

## Next implementation slices

1. Seed the approved department/category/type catalog and publish one controlled form definition per record type.
2. Add detail/edit/file/ACL endpoints and the four screens.
3. Add isolated database fixture, migration idempotency, record-level security, search and file integrity tests.
4. Start the local Supabase stack, apply migrations only to the local database, run focused tests and report coverage.
