# C-02 managed backups

Backups live under `/opt/ops/thoidai-work/backups/managed`, split into `daily/` and `predeploy/`. Each complete backup has `postgres.dump`, `storage.tar.gz`, and `manifest.txt`; `.partial` directories are unpublished. Retention keeps seven daily backups, one per ISO week for four weeks, one per month for three months, and five predeploy backups. `.keep` and unknown names are protected. `THOIDAI_BACKUP_MAX_MB` defaults to 500 MB with a 50 MB reserve; the script never deletes outside its own root.

Owner approval is required before installation. Run `install -m 0750 scripts/production/thoidai-backup.sh /usr/local/sbin/thoidai-backup`, copy the four units to `/etc/systemd/system/`, then `systemctl daemon-reload` and `systemctl enable --now thoidai-backup.timer thoidai-backup-status.timer`.

Restore drill: run `git show <sha>:scripts/production/backup-restore-drill.sh | ssh vps-aylaspa "bash -s"` from the approved commit. The drill selects the newest strictly named `YYYYMMDDTHHMMSSZ-daily` directory containing `postgres.dump` and `manifest.txt`, verifies the dump SHA-256 recorded in the manifest, and checks that `storage.tar.gz` is readable. It starts `public.ecr.aws/supabase/postgres:17.6.1.095` with `--network none` and `--memory 512m`, waits for `PostgreSQL init process complete`, three consecutive `pg_isready` probes, and the four required roles, then revokes the default `public` schema privileges before restoring only application data with `pg_restore --schema=public --schema=supabase_migrations -h 127.0.0.1 -U supabase_admin -d postgres` (owner-preserving, no `--clean`). If the temporary image already has `supabase_migrations.schema_migrations`, it is truncated before restore; otherwise `pg_restore` creates the schema. It prints `RESTORE_ERRORS` and the first 20 non-`already exists` errors, compares the seven required application/ledger table counts against production using read-only `psql`, and reports sanitized `psql` errors in `DRILL_ERROR`. The drill verifies application data (`public` plus the migration ledger); Supabase system schemas (`auth`, `storage`, `realtime`, extensions, vault) are supplied by the image. Disaster recovery still requires the same Supabase stack version; this is a known limitation. It ends with `DRILL_STATUS=PASS` or `DRILL_STATUS=FAIL`. It never runs `pg_dump`, restarts or writes production, or uses `docker top`/`inspect` on the production container. Offsite storage is deferred and needs an owner-provided destination.
